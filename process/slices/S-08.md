### 読み方

- **stress（実際のゲームに近い重さ）**: span は垂直同期なしのフレーム時間と 0〜7% の差で一致し、low < mid < high、DPR 1 < DPR 2 と負荷に比例して増える。
  three のパスの合計（5〜60ms、フレームの6〜14倍）とは違い、1フレームの GPU 時間として使える。
- **span を測る負担**: span あり/なしでフレーム時間の差は −4%〜+5%（0.02〜0.07ms）で、計測のばらつきの範囲。
- **hello（ほぼ空のシーン、毎秒 800〜4,500 フレーム）**: span がフレームの間隔より長い（2.4〜5.1倍）。定常状態で
  「1フレームの最初から最後まで」が「フレームの間隔」より長いのは、GPU が前後のフレームを重ねて実行しているとき（スループットが1フレームの
  レイテンシより速い）だけで、span はこのとき **1フレームのレイテンシ** を表す。小さなパス（透過の背景のミップ生成など）ばかりで GPU が埋まらない
  ときに起きると考えられる（仮説。three のパスの合計も DPR 2 では 2.57ms とフレームの間隔 1.25ms を超えており、重なりがあることと矛盾しない）。
- **垂直同期あり（参考）**: stress の span は 2.9〜4.6ms で、垂直同期なしの約3倍。60fps で待つ間 GPU の動作周波数が下がるため（S-05 で
  パスの合計にも見えた現象）。それでも縮める閾値（13.3ms）の 1/3 以下。hello は 0.9〜1.1ms。

## 判断

**span を governor の GPU 時間として採用し、Apple でも信用する**（受け入れ条件3を実施）。理由:

1. 動的解像度が働くべき場面（GPU が重い場面）では、span は実際の処理量（垂直同期なしのフレーム時間）と 0〜7% で一致した（stress、全段、DPR 1 と 2）。
2. hello で span がフレームの間隔を超えるのは、フレームが毎秒数千枚出て GPU 上で重なるときだけ。実行時は垂直同期の下でフレームが 16.7ms 離れているので、
   1フレームのレイテンシが更新間隔の大半を占めるまで重ならない。その場合も span は「このフレームが締め切りに間に合うか」を表すレイテンシで、
   動的解像度にとってはむしろ正しい量。過大に出る方向なので、間違っても解像度を下げすぎる側（安全側）に倒れる。
3. governor の妥当性の検査（GPU 時間の中央値が平均フレーム時間を大きく超えたら信用しない）は span にもそのまま効く。垂直同期なしの hello のような
   読みはここで止まる（強い混雑の閉ループで実際に止まった）。
4. 閉ループ（垂直同期なし、DPR 2）で、span は解像度に応じて下がり、制御は帯の中で落ち着いた（混雑ありの機能確認）。

残るリスク: 垂直同期の下では GPU の周波数が負荷に合わせて下がるので、軽い負荷では span が解像度に比例しない（M5 Pro で 3〜5ms のまま、混雑あり）。
縮める閾値（13.3ms）はその帯よりずっと上なので、この機械では解像度は最大のまま。周波数の制御が「GPU 時間を更新間隔の大半まで引き延ばす」機械では、
span が閾値の近くに張り付いて解像度を下げ続けるおそれがある。推奨環境の M1 で `scripts/bench-dynres.mjs`（垂直同期あり）を回して確かめる（S-07）。
起きたら「縮めても span が下がらなければ最大に戻して止める」判定を governor に足す（提案。いまは足していない）。

ただし受け入れ条件2の文言（「同程度以下」）は hello の垂直同期なしでは満たしていない。**この判断でよいかは親（発案者）の確認待ち。**
受け入れない場合は `chooseGpuTimeSource` で span の `trusted` を `apple` のときだけ false にすれば、S-05 の状態（Apple では動的解像度が止まる）に戻る。

## AGENTS.md への提案

- 「GPU のタイムスタンプを GPU 時間として信じない」の項を次に置き換える:
  **GPU 時間は span（フレームの最初のパスの開始から最後のパスの終わり、`src/core/perf/gpu-span.ts`）で見る。** three の `resolveTimestampsAsync` は
  描画パスごとの時間の合計で、Apple/Metal では重なって約10倍に膨らむので判断に使わない（参考値）。span は WebGPU だけで、Apple でも実際の処理量と
  0〜7% で一致した（S-08、stress）。毎秒数千フレームの軽いシーンでは、フレームが GPU 上で重なり span がフレームの間隔より長く出る。

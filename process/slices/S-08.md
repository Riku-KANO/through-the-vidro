## レビュー1巡目への対応（試行2）

| 指摘 | 対応 |

| P2-1 信用をやめたとき、下げた倍率のまま残る | **直した**。`PerfGovernor` は GPU 時間の信用をやめたら動的解像度を止め、倍率がプリセットと違えば次の `frame()` で `{kind:'scale', scale: presetScale(level)}` を返して bump する。止めた理由は `dynresStopReason`（プローブの `dynresStopped`）。単体テスト「信用 → 縮める → あり得ない値 → プリセットへ戻る」を追加 |

### テストの変更（既存のテストに手を入れたもの）

- `governor.test.ts`「dynamic resolution lowers the scale under GPU overload」と「keeps trusting real GPU overload under vsync」: GPU 時間を
  倍率によらない一定値（30ms、22ms）から、画素数に比例する値（`30 * (scale / 0.85) ** 2` など）に変えた。一定値は「縮めても下がらない」
  場面そのもので、P2-2 の検査では止まるのが正しい振る舞いになったため。確かめている中身（過負荷で倍率が下がる、量子化したフレームでも信用を保つ）は同じ。
- `?dynresTarget`（試験用の目標値）を付けたときは、手応えの検査を既定で切る（`?dynresResponse=1` で入れられる）。S-05 の e2e「dynamic resolution
  lowers the render scale under load」は、届かない目標で倍率が下限近く（0.6 以下）まで下がることを確かめているが、ヘッドレス・垂直同期ありの hello では
  span が解像度に比例しないので、検査を入れると 0.70 でプリセットへ戻り、この e2e が落ちた（両経路、確認済み）。S-05 の spec は書き込み範囲外なので、
  フックの既定で対応した。**提案**: 統合時に S-05 の spec に `&dynresResponse=0` を明示し、`dynresTarget` との連動をやめる。

### 読み方

- **stress（実際のゲームに近い重さ）**: 垂直同期なしで、span はフレーム時間と 0〜7% の差で一致し、low < mid < high、DPR 1 < DPR 2 と負荷に応じて増えた（2回とも）。
  three のパスの合計（4〜113ms）とは違い、1フレームの GPU 時間として使える。ただし垂直同期なしでは JS の render 時間もフレーム時間に近い
  （DPR 1 で 0.72〜1.22ms）。この状態では render() の中で GPU を待つ（バックプレッシャ）ので、CPU 律速か GPU 律速かはこの表だけでは決められない。
  DPR 2（画素4倍）でもフレーム時間と span がそろって増えたことが、GPU 側の負荷を span が追う根拠。
- **測る負担**: span あり/なし（−4〜+5%）、three のパスごとのタイムスタンプあり/なし（差は 0.03ms 以内）とも、フレーム時間の差はばらつきの範囲。
- **hello（ほぼ空のシーン、毎秒 800〜5,000 フレーム）**: span がフレームの間隔より長い（2.4〜5.1倍）。定常状態で「1フレームの span」が
  「フレームの間隔」より長いのは、前後のフレームの作業が GPU 上で重なっているか、印が three のパスを挟んでいない（開始の印が前のフレームの途中で
  書かれる）ときだけ。どちらかは区別できていない（**仮説**: 小さなパスばかりで GPU が埋まらず、前後のフレームが重なる。three のパスの合計も
  DPR 2 では 2.57ms とフレームの間隔 1.25ms を超えており、重なりがあることとは矛盾しない）。
- **垂直同期あり**: stress の span は垂直同期なしの 2.1〜6.3 倍（DPR 1 で約5ms、DPR 2 で 4.9〜9.1ms）。JS の render 時間（1.7〜2.0ms、
  垂直同期なしの約2倍）は負荷によらずほぼ一定で、span はその 2.5〜5.4 倍。JS の submit 待ちだけでは説明できず、残りは GPU の実行（待つ間の
  周波数の低下を含む）か、GPU プロセス（Dawn）の記録の時間か、その両方。この計測では区別できない。DPR 2 では負荷とともに span が増え、
  垂直同期なしとの比は小さくなる（3.0 → 2.1）ので、GPU 側の部分は負荷を追っている。縮める閾値（13.3ms）に対しては、M5 Pro では最も重い
  条件（DPR 2 high）でも平均 9.1ms。

## 判断

**span を governor の GPU 時間として採用し、Apple でも信用する。縮めても span が下がらなければ止める**（受け入れ条件3、親の判断 P2-2 案A）。理由:

1. GPU が重い場面では、span は実際の処理量（垂直同期なしのフレーム時間）と 0〜7% で一致した（stress、全段、DPR 1 と 2、静かな2回）。
2. 垂直同期ありの閉ループ（DPR 2 high）でも、span は解像度に応じて下がった。
3. span が負荷を追わない場面（垂直同期ありで軽い負荷、または画素で決まらない処理が多い場面）では、手応えの検査がプリセットの倍率へ戻して止める。
   GPU 時間が平均フレーム時間を超える読み（hello の垂直同期なし、強い混雑）は、従来の妥当性の検査で信用をやめ、これもプリセットの倍率へ戻す。
   どちらの場合も下げた倍率のまま残らない。

ただし受け入れ条件2の文言（「同程度以下」）は hello の垂直同期なしでは満たしていない（親が spine の文言を直す予定）。

**振る舞いの変更（記録と CHANGELOG に明記）**:
- (a) Apple の WebGPU で GPU 時間を信用するので、`quality=auto` の推奨と確かめも、フレーム時間ではなく span で行うようになった。
  `COST_FACTOR`（low 0.85 / mid 1 / high 1.7）は垂直同期なしのフレーム時間で較正した値で、垂直同期ありの span はそれより長く出る（上の表で 2〜6倍）。
  推奨の見積もりは span の値そのものを閾値（13.3ms）と比べるので、**低めの品質を選ぶ側に偏りうる**。M5 Pro では stress mid の垂直同期ありの span が約5ms
  なので high の見積もりは約8〜10ms で high を選ぶ。M1 では要確認（S-07）。
- (b) Apple 以外の WebGPU も、three のパスの合計から span に切り替わった（親の判断: 計測の方法を1つに揃える）。Iris Xe などで確かめる（S-07）。
- (c) `?dynresTarget`（試験用）を付けると、手応えの検査は既定で切れる（上の「テストの変更」）。

戻すとき: Apple で span を信用しないなら、`chooseGpuTimeSource` で span の `trusted` を `apple` のときだけ false にすれば、S-05 の状態に戻る。

## AGENTS.md への提案

- 「GPU のタイムスタンプを GPU 時間として信じない」の項を次に置き換える:
  **GPU 時間は span（フレームの最初のパスの開始から最後のパスの終わり、`src/core/perf/gpu-span.ts`）で見る。** three の `resolveTimestampsAsync` は
  描画パスごとの時間の合計で、Apple/Metal では重なって約10倍に膨らむので判断に使わない（参考値）。span は WebGPU だけ。M5 Pro の stress では実際の処理量と
  0〜7% で一致したが、2つの印がパスを挟むことは保証されない（毎秒数千フレームの軽いシーンでは span がフレームの間隔より長く出る）。垂直同期ありでは
  2〜6倍に長く出る。動的解像度は、縮めても span が下がらなければ止まる。性能の比較は従来どおり垂直同期を外したフレーム時間（`scripts/bench-headed.mjs`）で行う。
- 「Metal では作業のないパスのタイムスタンプは 0 のまま」: 自前でタイムスタンプを置くパスには必ず何か dispatch / draw する。
- URL スイッチに `gpuSpan=0`、`gpuPasses=0`、`dynresResponse=0|1` を足す。コマンド表に `scripts/bench-dynres.mjs` と、bench-headed の `DPR`、`VSYNC=1`、`OUT`、`QUERY` を足す。
- 「GPU への submit は render() の中で行う」（`scene.ts` に書いた約束）をシーンの契約の説明に足す。

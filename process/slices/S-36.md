   WebGPU で 150〜225 ms のフレームが出た（CPU の `render()` は短く、GPU のパイプラインのコンパイルが後のフレームを待たせる）。
   組み立て終えたら three の `compileAsync` で、覗く像の描画先と scene pass と同じ形式の描画先へ裏でコンパイルするようにした。
   温めのフレームは最大 29 ms（WebGPU）。透過のガラス（部屋1の雫）は compileAsync に入れない（AGENTS.md）。部屋1の雫は序章の雫と
   同じ形と材質にして、読み込みで作ったパイプラインを使う。
2. **部屋1の覗く絵の測り方の誤り**（e2e 赤 3）: 玉の円を正規化した座標のまま画素として切り出していた。画素（×1280、×720）に直した。
3. **視界の中で足す判定が過ぎた**: 初めはエリア1全体の箱 1 つで視錐台を判定し、WebGL2 の座標系（`camera.coordinateSystem`）を
   渡していなかった。物ごとの箱（`bounds`）と座標系を渡すようにした。
4. **InstancedMesh のシェーダは描画コンテキストごとに別のコード**（レビュー 1 巡目 P2-4、赤の証跡 5）: three r186 の InstancedMesh は
   行列を node の id の名前の uniform buffer（`NodeBuffer_<id>`）に書く。RenderObject の鍵に描画コンテキストが入るので、コンテキスト
   ごとに node を組み直し、シェーダのコードが変わる（WebGL2 のプログラムの鍵はコードだけ、WebGPU はコードと形式）。描画コンテキストは
   `RenderContexts.get(renderTarget, mrt, callDepth)` で attachment の形式・mrt・**呼び出しの深さ**ごとに 1 つ。`compileAsync` は深さ 0
   （覗く像と同じコンテキスト）で作るので、scene pass（`pass()` の中、深さ 1）の分は作れない（scene pass と同じ形式の描画先へのコンパイルも、
   覗く像のコンテキストに入る。ふつうの Mesh はコードと形式が同じなのでそれで足りる）。エリア1の光の粒を、頂点（62 粒 × 60）を CPU で
   毎フレーム書く 1 つの Mesh にした。温めのフレームは最大 30 ms（WebGL2）、autoplay のエリア1の段の最長 41.5 ms（WebGL2）・39 ms（WebGPU）。
5. **組み立てを始める所**: 広場の縁（坂の下）で始めると、autoplay は 0.5 秒後に東を向くので、裏のコンパイルが 0.35〜0.47 秒かかった回
   （`?debug=1` の調べで遅くなる）は、道に出るまで視界の外のフレームがなく、道で視界の中に足された（`addedInView` が両経路で true、
   最長フレーム 105〜107 ms: 足したフレームに全部の物の node を組んだ）。坂の上の峠（`SLOPE.fromZ`）を越えたら始めるようにした。
   組み立てとコンパイルは 1 秒以内に終わり、坂を下りる間（南向き）に視界の外になったフレームで足す（e2e: 峠で始まり約 23 秒後、
   坂の途中で足した。両経路で `addedInView` false）。東（煙突）を見たまま下りると、坂の下まで視界の外にならない（下の「判断待ち」1）。

   そうしても温まらない（three r186、S-36）。** `compileAsync` は描画先の形式と呼び出しの深さ 0 の描画コンテキストで作る。ふつうの Mesh は

   buffer（`NodeBuffer_<id>`）に書くので、コンテキストごとにシェーダのコードが変わり、scene pass が初めて描くフレームで作られる
   （WebGL2 で 125 ms）。後から足す物の InstancedMesh は、頂点を書く 1 つの Mesh にするか、読み込みの温めの姿勢で見える所に置く。

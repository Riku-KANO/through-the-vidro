### S-06 の e2e の変え方（通しを門まで伸ばす分だけ）

- 通し（実際の入力）: 雫の後の「罰がない: 岸で拾うと橋が消える、すぐ橋へ踏み出しても落ちない」は、雫の後では橋が消えなくなったので、
  雫の前（橋の上で拾えない、の直後）へ移し、拾った後に置き直してから渡る。雫の後は、光と門を待つ → 橋を戻る → 橋の上で拾う
  （拾えて、当たり判定は全区画のまま、球は0）→ 向こう岸へ → 門をくぐる → 柵で止まる、を足した。
- autoplay: 終わったときに、`pickup:pedestal` があり `shake:pickup` がない（橋の上で拾えた）、玉は手、門は開き、当たり判定は全区画、門の先にいる、を足した。

## 分かったこと（失敗をルールに変える）

1. **部屋の出来事の記録（`room.events` → `probe.events`）に新しい種類を足すと、S-16・S-18 の e2e が落ちる。** 両方の e2e は記録の
   すべての名前を音の表（`CUES`）と照合し、知らない名前があると `no sound decided for the event` で投げる。S-16 の通しは雫の後まで
   進むので、締めの出来事をそこへ流すと必ず赤になる。締めの出来事は別のバス（`room.finale`、セッションの `finaleEvents`）に流し、
   音もキューの記録（`played`・`voicesStarted`）とは別に数えた（`probe.finale`）。AGENTS.md に提案2。
2. **波面の光輪は、近くで見る大きな面を丸ごと持ち上げる。** 最初の作り（幅 0.32m のガウス、強さ 3）では、向こう岸から振り返ると波面の手前の
   床・欄干・手すりが全部クリーム色に飛んだ（ブルームを切っても同じ。光輪そのものの量）。実体化の境目と同じ「細い線＋淡い光輪」にして、
   光輪を線の 8%・0.3m に絞った。それでも波面がカメラの 2m 以内を通る間は画面の下がかぶった（レビュー P3-4）ので、膜・灯籠・光の粒と同じく
   目から 0.8〜2.6m で弱める。橋のアーチ（波面と同じ向きの輪）は通り過ぎる瞬間に輪ごと光る。
3. **「表の層の気配」を定着で消すなら、気配が動く範囲まるごとを定着の箱に入れる。** 光の粒は縁から向こう岸の上 1m まで流れる。箱を橋の端で
   切ると、定着の後に粒が向こう岸の上の見えない面から湧いて出た（レビュー P2-1）。箱を粒の流れの終わりまで広げ、layout.test で粒の道筋の
   両端が箱の中にあることを確かめる（粒の流れの長さは room-art.ts にも同じ式があるので、変えるときは `MOTES_END_Z` と揃える）。

## 長いフレームの原因（レビュー 2 巡目 P2-3）

S-06 の autoplay（WebGPU）の最長フレームが 200ms の判定に近かった件（全検査 2: 遊ぶ間 191ms）。**原因は締めの段ではなく、工房の透過ガラスの
小物（S-24・S-27 の glb）のパイプラインを、向こう岸から振り返ったときに初めて作るコンパイル**だった。

- 並列のセッション（S-26 ほか）の Playwright のブラウザが動いていたので、`QUIET=1` の計測（混雑なら中止）はできない。代わりに、同じ実行の中で
  条件を交互に入れ替えて比べた（混雑は両方に同じようにかかる）。
- 部屋が autoplay の段ごとに自分の更新の間隔を測るようにした（`probe.autoplay.worstMs`・`worstStep`・`steps`。S-06 の e2e が phases の記録に
  `gameSteps` として書く）。WebGPU の autoplay を 3 回: 遊ぶ間の最長 194.7 / 42.4 / 41.5 ms で、**3 回とも段 `look-back`**（雫を取った後に
  振り返る 2.5 秒）。ほかの段は 17〜24 ms。
- 締めを切る一時的な切り替え（コミットしていない）で、締めあり・なしを同じ実行で 3 往復（直接始める autoplay）: `look-back` の最長は
  あり 33.7・32.9・42.6 ms、なし 43.6・32.0・39.9 ms で差がない。時間は描画（`render`）の中で、更新（`update`）は 1.3 ms 以下。
- three のパイプラインの数を段ごとに数えた（`debug=1`）: `look-back` の部屋の時刻 25.8 秒あたりで、6 フレーム続けて新しい描画パイプラインと
  フラグメントのプログラムが 1 つずつ（計 8）作られる。中身は `A0_ware_frost01`・`A0_ware_clear01`・`A0_ware_bubble01`・`A0_anl_annealer01`・
  `A0_ware_anneal01`・`A0_tub_water01`・`A0_ware_cart01`・`A0_ware_marver01`（どれも透過のガラス。仕上げの scene pass の描画先）。工房のドームの
  奥（+Z 側）にあり、台本は着地からずっと -Z を向いているので、向こう岸で振り返るときに初めて視界に入る。S-24・S-27 の同じ計測で
  25〜47 ms だったのと同じ種類で、混雑の中ではコンパイルが 195 ms まで延びる。
- 着地の前の読み込み中に、作業台の前から後ろ向きにもう一度描く案を一時的に試したが、`look-back` は 26〜52 ms のままだった（同じ描画先・
  同じ透過の背景の状態で描かないと、同じパイプラインにならないとみる）。直すのは部屋の温め方（S-24・S-27・S-26 の範囲）として提案 5 にした。
  S-34 の範囲では直していない。
- 直した後（門の時機、確保の直し）の S-06 の autoplay（全検査 3 の前の単独の流し）: 遊ぶ間の最長 WebGPU 38.0 ms・WebGL2 62.5 ms（どちらも
  `look-back`）、潜る遷移 18.5 ms・28.7 ms。締めの段そのもの（光が渡る間と門が開く間）の確保は、レビュー 2 巡目 P3-1〜P3-3 で減らした
  （定着した区画の一覧は数が増えたときだけ、扉の当たり判定と定着の音の位置は確保なし）。

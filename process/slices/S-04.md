### 潜る遷移の仕組み（1カットでつなぐ方法）

1. ゲーム側のシーンを毎フレーム、ゲームのカメラで画面と同じ解像度の別画像（HalfFloat）に描く。
2. ホームの玉は、その画像を画面上の位置で、玉の表面での屈折（屈折率1.5）だけずらして読む。縁は厚いガラスとしてわずかに暗く緑に、反射と光の帯を足す。
3. 潜る間、外のカメラは玉へ近づき、ゲームのカメラは街の縮図の視点 → 工房のドームの真上 → 天窓を通って → 作業台の前（目の高さ1.6m、視野角70度）へ動く。
   外のカメラが玉の表面を通り抜ける瞬間（曲線上の進み 0.62）と、ゲームのカメラがドームの天窓を通る瞬間が重なるように道筋を置いた。
4. 玉が画面全体を覆ってから（単体テストで 4:3〜21:9 の全比率を確認）、同じシェーディングを画素ごとに玉の表面を計算し直す全画面の映像へ引き継ぐ
   （曲線上の進み 0.55〜0.62、時刻で 0.846〜0.898秒）。同じ式なので継ぎ目が出ない。引き継ぎの間から、玉と全画面の映像の両方に同じ
   「全画面の樽型の歪み」と「中心から外へ走る波紋の輪」が立ち上がり、通り抜ける瞬間（0.898秒）に最大になる。その後、ガラスの表面の効果・屈折・歪みが 0 まで緩む。
   樽型の歪みの半径は画面の四隅までの距離で正規化し、縦横比によらず同じ引き方にした。屈折・縁の帯・樽型の歪み・波紋を合わせた画面のずらしを
   `src/ui/home/lens-math.ts` に純粋関数として写し（定数はシェーダと共有）、4:3・16:9・21:9 のどの時点でもずらしのヤコビアンの行列式 > 0.25、
   傾き > 0.4（像が折り返さない）を単体テストで確かめている。
5. 遷移の最後には全画面の映像がゲーム側の画像そのものになり、そこから先はゲーム側のシーンを画面に直接描く（同じ画像なので切り替わりが見えない）。

### 事前のシェーダのコンパイル（S-00 の 1.2秒の停止への対処）

読み込み中に `renderer.compileAsync` を描き先ごとに行う: ホームの玉と全画面の映像（隠れている物も一瞬だけ表示状態にして集める）→
ゲーム側を別画像向けに → ゲーム側を画面向けに（同じ形式なのでキャッシュに当たり 0ms）→ 別画像へ一度だけ実際に描く。
遷移の間の最長フレームは両経路で 18ms 以下（下の表）。

## 分かったこと（失敗をルールに変える）

1. **曇りガラスが効かなくなる罠**: `backdrop-filter` は、祖先に `opacity < 1` や `will-change: opacity` があると背後の景色を見られず、曇りが消える。
   雫の出現のフェードは雫そのものではなく子要素（玉と札）に掛けた。→ AGENTS.md の技術の決まりごとに足す提案（下）。
2. **AgX は線形1付近を灰色に寄せる**: 白い霧は線形 2〜3 にしないと白く見えない。暗い青も持ち上がる。
3. **計測値が消える時機**: three r186 の `renderer.info` はアニメーションループの1フレームに1回、`update` の前に消える（`Animation.js`）。
   複数パスのシーンでも main の予算判定は全パスを数えている。シーンの側でフレームの数値を読むなら `render()` の後で読む。
   （レビュー前は「render() ごとに消える」と書いて autoReset を書き換えていたが、誤りだったので取り下げた。）
4. **プローブは1フレームごとに更新される**: e2e で入力の直後に読むと古い値になる。入力の後は `waitForFunction` で待つ（テストはそうした）。
5. **画面空間のずれで像が折り返す**: ずれの写像のヤコビアンの行列式が 0 以下になると、像が裂けたり裏返って二重に見えたりする
   （波紋で真鍮の骨が「鉤」になった、21:9 の左右の端で樽型の歪みが折り返した）。波紋は 振幅 × 周波数 × 2 × 縦横比 を小さく、樽型の歪みは半径を四隅で正規化する。
   縁へ向けて増える外向きのずれは折り返さない。複数のずれは合わせて効くので、全部を写した純粋関数で縦横比ごとに確かめる（`lens-math.test.ts`）。
6. **戻る操作は冪等に**: Esc で `reverse()` を呼ぶだけだと、2回目で前へ戻り、押しっぱなし（キーリピート）で行ったり来たりする。戻る向きなら何もしない形にした（単体テストあり）。

## S-05 からの共有への対応: 透過の材質と別画像の大きさ（WebGPU）

共有された不具合: 透過（transmission）の材質を、canvas と違う大きさの RenderTarget へ同じフレーム内に描いてから本描画すると、
WebGPU 経路で毎フレーム「Destroyed texture [RGBA16Float] used in a submit」が出て描画が捨てられる（WebGL2 では出ない）。

S-04 での確認（2026-10-21、ヘッドレス Chromium。f76f422 のビルドで全種類の console を集めて確認し、その後の最終のビルドでも S-04 の e2e〈GPU の検証の warning も失敗に数え、窓の大きさの変更を含む〉が緑）:
- 台本を最後まで再生し、ホームで玉がゲーム側の画像を映している間と工房の中で、窓の大きさを変えた（1280×720 → 1000×640 → 1280×720、工房で 1100×700）。
  console の全種類（error / warning / info / log）を集めたところ、**WebGPU・WebGL2 ともメッセージ0件**、`__vidro.errors` も空。スクリーンショットも両経路で同じ絵。
- 当てはまらない理由:
  1. 透過の材質（作業台の器3つ）があるのは、玉の中の別画像へ描く層だけ。同じフレームの canvas への描画（ホームのシーン）には透過の材質がない。
  2. 別画像は常に描画バッファと同じ大きさ（`renderer.getDrawingBufferSize`）。
- 判断: 玉の中身は「ゲーム側のシーンそのもの」（遷移の一覧）なので、ゲーム側の材質から透過を外すことはしない。代わりに次の2つを守る。
  - 玉の中の別画像は、毎フレーム描く直前に描画バッファの大きさと比べ、違えば合わせる（`home-dive.scene.ts` の `render()`）。
    窓の大きさが変わらず描画の倍率だけが変わる場合（S-05 の動的解像度）でもずれない。
  - ホームのシーン（canvas へ描く層）には透過の材質を置かない。玉の屈折は `texture(別画像, screenUV + 屈折のずれ)` の自前の合成で描く（今の作り）。
- 再発の検出: `tests/e2e/S-04-home-dive.spec.ts` は console の error に加えて、warning に出る GPU の検証エラー（`Destroyed texture` / `GPUValidationError` / `used in a submit`）も失敗として数える。
  入力のテストに、ホームでの窓の大きさの変更を足した。
- 統合（S-05 / S-06）への申し送り: 動的解像度で描画の倍率を変えるときも、別画像を描画バッファに合わせる必要がある（上の毎フレームの照合で満たす）。
  S-06 でホームのシーンに透過の材質を足す場合は、この不具合の条件に当たるので避ける。

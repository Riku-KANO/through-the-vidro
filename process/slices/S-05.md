## 分かったこと・決めたこと

1. **WebGPU で、画面と違う大きさの RenderTarget に透過の材質を描くとフレームが捨てられる（r186）。** 「Destroyed texture used in a submit」が
   毎フレーム出る。WebGL2 では出ない。S-02（覗くパス）と S-04（ホームの玉の縮図）に共有し、AGENTS.md に追加した。
   画面と同じ大きさの描画先（`pass()` による仕上げのパス）では問題がないことを負荷シーンで確認した。
2. **GPU のタイムスタンプは Apple/Metal では GPU 時間として使えない。** three は描画パスごとの時間を合計し、約20パスになると重なって約10倍に膨らむ
   （実際 1.1ms のフレームが 11〜22ms）。WebGL2 のタイマーも約2倍だった。そこで:
   - 性能の比較は垂直同期を外したフレーム時間で行う（bench-headed）。
   - 実行時は、Apple/Metal の GPU 時間を判断に使わない（表示と計測には使う）。それ以外でも、GPU 時間の中央値が平均フレーム時間を超えたら信用しない。
   - **信用できる GPU 時間がないとき、動的解像度は止める。** 垂直同期の下ではフレーム時間で「上限」と「過負荷」を見分けられず、中くらいの過負荷を
     まったく隠してしまう（レビュー2巡目の模擬で確認）。このため推奨環境の M1 では、M0 の時点で動的解像度は働かない。
   - 品質の自動選択と検証は、GPU 時間がなければフレーム時間（取りこぼしとジッタ）で行う。60Hz の画面では上げる判断はできない（mid のまま）。
3. **影のカメラの layers を明示しないと、覗くパスの後で表の層の物が影を落とさない。** AGENTS.md に追加した（S-02 にも共有）。
4. **プリセットの差は解像度だけではない。** 品質の見積もりは段ごとの係数（low 0.85 / mid 1 / high 1.7、high は上げる判断にだけ使うので控えめ）にした。
5. 動的解像度の下限（プリセットの60%、かつ0.5以上）は設計書にない値。1080p でガラスの縁と文字が読める範囲として決めた。M1 の UI と一緒に見直す。
6. **設計書の「透過の背景画像 1/4・1/2・等倍」は未実装。** r186 の透過は背景画像の解像度を公開の API で変えられない。負荷シーンの計測と係数は、
   全プリセットで等倍の透過背景のまま較正した。担当は S-01（ガラス材質）か M1 で決める。実装したら係数を較正し直す。

## 作ったもの

- `src/core/perf/governor.ts`: 自動選択・検証・動的解像度をまとめた状態機械（計測 → 切り替え → 検証 → 定常）。GPU 時間の妥当性、作り直しの失敗からの復帰
- `src/core/perf/quality-select.ts`: 推奨プリセットの判定、GPU 時間とフレーム時間それぞれの検証
- `src/core/perf/dynamic-resolution.ts`: GPU 時間による動的解像度
- `src/core/renderer.ts`: timestamp query、GPU の名前、Apple/Metal の判定
- `src/core/params.ts`: `quality=auto`、`autoWindow`、`autoFrom`、`autoForce`、`dynres`、`dynresTarget`、`gpuTrust`
- `src/main.ts`: governor の組み込み（シーンの作り直しと15秒の上限、失敗時の復帰、GPU 時間の取得は使うときだけ8フレームに1回、console.error をプローブへ）、`?debug=1`
- `src/dev/stats.ts`: GPU 時間（信用しないときは印）、テクスチャと形状のメモリ、品質と倍率
- `src/scenes/stress.scene.ts`: 負荷シーン（`?peek=0` で覗くパスなし）
- `scripts/lib/preview-server.mjs`、`scripts/bench-probe.mjs`、`scripts/bench-headed.mjs`

# S-12 高品質で描画倍率を変えた後に出る Destroyed texture の調査と修正

状態: **green（レビュー1巡目の指摘を直した。2巡目は親）** · ブランチ `slice/S-12-resize-destroyed`（main b880b8b から。途中で S-11 入りの main 98185af を取り込んだ） · 担当: サブエージェント

## 結論

- **three r186 の不具合。** ノードを1つも持たない透過の材質（`MeshPhysicalNodeMaterial({ transmission: 1 })` だけで作ったもの）の物は、
  描画の大きさが A → B → A と変わる間に画面外にいて、その後に視界に戻ると、破棄済みの透過の背景画像のまま描かれる。
  - WebGPU: `Destroyed texture [… RGBA16Float] used in a submit` が毎フレーム出て、その submit（仕上げのパスの描画全体）が捨てられる
  - WebGL2: `WebGL: INVALID_OPERATION: bindTexture: attempt to use a deleted object`（S-11 の報告では「WebGL2 では出ない」だったが、
    同じ原因で別の警告が出ていた）
- **起きていたのは負荷シーン（stress）だけ。** 高品質に限らず、中品質でも起きる（低品質も近景のガラスは同じ作り。低は確かめていない）。高品質は遠景のガラスも透過になるので
  約18秒後に出て、中品質は近景のガラスがカメラの一周で戻る約34〜36秒後に出る（25秒では見えなかった）。
  prologue-proto と glass-gallery は `createGlass()` のガラス（必ず `thicknessNode` を持つ）なので起きない。
- **直し方**: 共通部品に `src/core/glass/backdrop.ts` を足し、負荷シーンの手作りの透過の材質2つに `followBackdropResize()` を通した。
  材質に、three の既定と同じ値のノード（`thicknessNode = materialThickness`）を入れて、three に毎フレーム更新させる。公開の API だけを使う。
- 「約20秒の遅れ」は three のキャッシュの解放の周期ではなく、**カメラの経路**（画面外にいた物が視界に戻る時刻）。

## 再現

- 手順（S-11 の報告どおり）: `?scene=stress&quality=high&dynres=0&debug=1` → 起動から約2秒後に `window.__vidroDebug.setScale(0.95)`

- WebGPU: 約17.6〜19.9秒後から `Destroyed texture [Texture (unlabeled 1280x720 px, TextureFormat::RGBA16Float)] used in a submit.
  While calling [Queue].Submit([[CommandBuffer from CommandEncoder "renderContext_7"]])` が error と warning の両方で毎フレーム
  （25秒の間に約415回ずつ）。`renderContext_7` は仕上げのパス（`pass(scene, camera)`）の描画。出ている間は自前の GPU 時間（span）が約2ms に下がる

- 倍率を変えなければ起きない。A → B だけ（戻さない）なら、戻ってきた物は「描画先の大きさが前回と違う」ので three が更新し、仕組みの上では

## 切り分けの経過

調査用のスクリプトとフックは scratchpad に置いた（リポジトリには入れていない）。ページの初期化前に `GPUTexture.prototype.destroy`、
`createView`、`GPUDevice.prototype.createBindGroup`、`GPURenderPassEncoder.prototype.setBindGroup` を包み、`?debug=1` の renderer から
three の `backend.createTexture`（GPU テクスチャに three の ID のラベルを付ける）、`backend.draw`（破棄済みのテクスチャを参照するバインドグループを
使った描画を、物・材質・描画先つきで数える）、`renderer.copyFramebufferToTexture`（背景画像をどの描画先から写したか）を包んだ。

1. **どのテクスチャか**: 破棄の記録では、エラーの出る約17秒の時点に新しい破棄はない。破棄されたのは `setScale(0.95)` の瞬間（と `setScale(1)`）で、
   使われているのはそのとき破棄された GPU テクスチャ。ラベルを付けると `Destroyed texture [Texture "T60:fb"]` になり、three の
   **FramebufferTexture（透過の背景画像）** と分かった。仕上げのパスの描画先（`output`、RGBA16Float）から写される FramebufferTexture は2枚あり、
   1枚は透過の背景画像（T60、エラーの対象）、もう1枚はおそらく手の玉の `viewportSharedTexture`（T18。確かめていない）。どちらも大きさが変わるたびに
   作り直される（版が上がる）。
2. **どの物・材質か**: 破棄済みの背景画像を参照するバインドグループ（`bindGroup_object`）を使っていたのは Mesh#170・#175・#220 など、
   材質 `MeshPhysicalNodeMaterial#36`。物の ID の範囲から**遠景のガラス**（`farGlass`、高品質だけ透過）。そのバインドグループは倍率の変更の
   **前**（−2.0秒）に作られたもの。中品質では Mesh#45・材質 #35（**近景のガラス** `nearGlass`）が、約34秒後に同じ形で出た。
3. **いつ描かれていたか**: Mesh#170 は −2.0〜−0.3秒と 17.8秒以降、Mesh#175 は −2.0〜−0.5秒と 17.6秒以降だけ描かれた。倍率を変える直前に
   画面外へ出て、変わっている間は描かれず、視界に戻った瞬間からエラーになる。**遅れはカメラの経路で決まる**（負荷シーンのカメラは
   `t` だけで動き、遠景の輪は約18秒後に視界に戻る。近景は一周 50m ÷ 1.4m/s ≈ 35.7秒で戻る）。
4. **なぜバインドが古いままか**: その物について three の `Bindings._update`（バインドの作り直しの判定）が一度も呼ばれていなかった。
   r186 の `Renderer._renderObjectDirect` は `NodeManager.needsRefresh()` が `NONE` を返すと、ノードとバインドの更新を飛ばして前の
   バインドグループのまま描く。判定は `NodeMaterialObserver.needsRefresh()`（下の「原因」）。
5. **WebGL2**: 同じ手順で、同じ時刻（19.9秒）から `bindTexture: attempt to use a deleted object` が出た。WebGL2 の backend もバインドを作るときに
   テクスチャの GL オブジェクトを控え（`WebGLBackend` の sampled texture の `textureGPU`）、作り直しの判定まで古いものを使う。
6. **ほかのシーン**: 高品質で同じ手順（30秒）を hello・audio-lab・home-dive・layers-lab・walk-lab でも試し、どれも出なかった。prologue-proto
   （`direct=1&autoplay=1`）と glass-gallery は試行1の e2e で直す前から緑（試行2で e2e から外した）。
7. **最小の再現**（three だけ、下に全文）: 2つの透過の玉で同じ材質、片方を隠して倍率を 1 → 0.75 → 1、隠した玉を戻す。両経路で再現し、
   `thicknessNode = materialThickness` で両経路とも消えた。玉が1つだけ（隠している間に透過の物が何も描かれない）だと、背景画像が作り直されず起きない。

## 原因

three r186 の2つの仕組みの組み合わせ。

- **背景画像の作り直し**: 透過の材質は、背景画像（`ViewportTextureNode` の FramebufferTexture。前面の透過は全材質で1つのノードを共有し、
  描画先ごとに1枚）を読む。透過の物を描くたびに、描画先の大きさと違えば大きさを変えて版を上げ、`Textures.updateTexture` が古い GPU テクスチャを
  破棄して作り直す（`backend.destroyTexture`。描画先の破棄 `_destroyTexture` と違い、参照しているバインドグループの記録を消さない）。
  バインドグループは、物ごとに `Bindings._update` が「テクスチャの世代が変わった」と気づいたときに作り直される。
- **物ごとの更新の省略**: `NodeMaterialObserver.needsRefresh()` は、材質にノードの性質が1つもない（`hasNode` が false）物について、
  ワールド行列・材質の値・形状・描画先の大きさ（`renderObject.context` の幅と高さ）・光源などが**その物を前回描いたとき**と同じなら `NONE` を返す。
  背景画像はこの比較に入っていない。材質ごとに1フレームの最初の物は `SHARED` になるが、これも共有の uniform しか更新しない。

そのため、透過の物 X が画面外にいる間に大きさが A → B → A と変わり、その間に視界にある別の透過の物が背景画像を B で作り直し、さらに A で作り直すと、
X が戻ったときには「描画先の大きさは前回と同じ A」なので更新が省かれ、X のバインドグループは最初の A の（破棄済みの）背景画像を指したまま描かれる。
物が動いている（ワールド行列が変わる）か、材質がノードを持っていれば毎フレーム更新されるので起きない。

- 高品質だけに見えた理由: 遠景のガラス（100個）が高品質だけ透過で、カメラの揺れで約18秒後に視界に戻る。近景のガラス（全品質で透過）は
  カメラの一周（約35.7秒）でしか戻らないので、25秒の確認では見えなかった。
- prologue-proto・glass-gallery で起きない理由: 透過のガラスはすべて `createGlass()` で作られ、`thicknessNode`（厚みのムラ）を必ず持つ。
- AGENTS.md の「画面と違う大きさの RenderTarget に透過の材質を描かない」との関係: 症状（破棄済みの背景画像を使う）は同じだが、最小の再現で
  毎フレーム半分の大きさの描画先にも同じ玉を描いても、修正の有無にかかわらずエラーは出なかった。規則の場面を最小の形で再現できなかったので、
  同じ原因とは言えない。規則はそのまま残す（S-02・S-04 の回避策も変えない）。

## 直し方

- `src/core/glass/backdrop.ts`（新規、core）
  - `followBackdropResize(material)`: ノードを持たない透過の材質に `thicknessNode = materialThickness` を入れる。three は `thicknessNode` が null の
    ときに `materialThickness` を使うので、値も見た目も変わらない。three はノードの性質を持つ材質の物を毎フレーム更新するので、背景画像の
    作り直しに追いつく。ノードを持つ材質と透過でない材質には何もしない。transmission を決めた後、最初に描く前に呼ぶ（three はノードを持つかを
    シェーダを組むときに決めるので、描いた後なら `material.needsUpdate = true` も要る）。
  - `missesBackdropResize(material)`: 危ない材質（透過で、ノードを持たない）の判定。`readsBackdrop`（three の `useTransmission` があればそれ。
    `src/layers/field.ts` の `isTransmissive` と同じ判定。layers 側から使うかは親が統合時に決める）、`hasNodeProperty` も公開。
- `src/scenes/stress.scene.ts`: `nearGlass` と、高品質の `farGlass` に `followBackdropResize()` を通した。
- `createGlass()` は変えていない。透過のガラスはもともと `thicknessNode` を持ち、単体テストで全種類×全品質×全配置×全役割を確かめた。
- 選んだ理由
  - three の非公開の内部に触らない。材質の公開の性質（`thicknessNode`）と公開の TSL（`materialThickness`）だけ。
  - 頼っているのは「ノードを持つ材質は毎フレーム更新される」という three の振る舞い。単体テストは three 自身の `NodeMaterialObserver`
    （`three/webgpu` から公開）の `needsRefresh()` を、最小の偽の RenderObject で何も変わらない3フレーム呼び、更新の種類を直接確かめる
    （回避策を通した材質は `[FULL, FULL, FULL]`、手作りのままは `[FULL, SHARED, SHARED]`）。three の更新で判定や内部の形が変われば、
    値が変わるか例外で単体テストが落ちる。e2e も残る。
  - 負荷シーンを本番のガラス（`createGlass()`、毎フレーム更新される）と同じ扱いにすることにもなる。
- 退けた案
  - 倍率の変更のたびに材質の値を少しずらして three に気づかせる、`scene.environmentIntensity` をずらす: 比較の中身（非公開の振る舞い）に頼り、
    見た目の値を変える。
  - `material.dispose()` で物を作り直させる: シェーダとパイプラインの解放と作り直しが走りうる。
  - 透過の物を視錐台で間引かない（`frustumCulled = false`）: 後ろの遠景のガラスまで毎フレーム描くので、描画呼び出しが予算（300回）を超える見込み（測っていない）。
  - main.ts で倍率の変更のあとに全部の物を更新させる: three の非公開の内部（RenderObjects など）が要り、main.ts は範囲外。

## three への報告用の最小の再現

three 0.186.1、Chromium（WebGPU と WebGL2 の両方で再現）。光源が1つは要る（照明モデルがないと透過が働かず、背景画像を写さない）。
`?webgl=1` で WebGL2、`?fix=1` で回避策。

```js
import { materialThickness } from 'three/tsl';
import * as THREE from 'three/webgpu';

const params = new URLSearchParams(location.search);
const renderer = new THREE.WebGPURenderer({ forceWebGL: params.get('webgl') === '1' });
renderer.setSize(640, 360);
document.body.appendChild(renderer.domElement);
await renderer.init();

const scene = new THREE.Scene();
scene.background = new THREE.Color(0x335577);
scene.add(new THREE.HemisphereLight(0xffffff, 0x444444, 2));
const camera = new THREE.PerspectiveCamera(50, 640 / 360, 0.1, 100);
camera.position.set(0, 0, 5);
const box = new THREE.Mesh(new THREE.BoxGeometry(2, 2, 2), new THREE.MeshBasicNodeMaterial({ color: 0xff8800 }));
box.position.set(0, 0, -3);
scene.add(box);

// A transmissive material without node properties.
const glass = new THREE.MeshPhysicalNodeMaterial({ transmission: 1, roughness: 0, thickness: 0.5 });
if (params.get('fix') === '1') glass.thicknessNode = materialThickness; // same value as the default
const geometry = new THREE.SphereGeometry(0.8, 32, 16);
const first = new THREE.Mesh(geometry, glass); // stays in view: recreates the backdrop at each new size
first.position.set(-1, 0, 0);
const second = new THREE.Mesh(geometry, glass); // hidden while the size goes 1 -> 0.75 -> 1
second.position.set(1, 0, 0);
scene.add(first, second);
camera.lookAt(0, 0, -3);

const steps = [
  [10, () => {}],
  [10, () => { second.visible = false; }],
  [10, () => { renderer.setPixelRatio(0.75); }],
  [10, () => { renderer.setPixelRatio(1); }],
  [30, () => { second.visible = true; }], // from here, every frame:
  // WebGPU: Destroyed texture [Texture (unlabeled 640x360 px, TextureFormat::RGBA16Float)] used in a submit.
  // WebGL2: WebGL: INVALID_OPERATION: bindTexture: attempt to use a deleted object
];
let step = 0;
let left = 0;
renderer.setAnimationLoop(() => {
  if (left === 0) {
    if (step >= steps.length) return renderer.setAnimationLoop(null);
    const [frames, action] = steps[step++];
    action();
    left = frames;
  }
  left--;
  renderer.render(scene, camera);
});
```

確かめた結果（Playwright、ヘッドレス Chromium、Apple M5 Pro）: 修正なしは WebGPU で `Destroyed texture … used in a submit` が 30回（error と
warning）、WebGL2 で `attempt to use a deleted object` が 30回。`?fix=1` は両経路で0。`second` を初めから出さず `first` だけにすると、隠している間に
透過の物が描かれず背景画像が作り直されないので起きない。

報告に書く要点: `NodeMaterialObserver.equals()` が、透過（`useTransmission`）の材質について背景画像（`ViewportTextureNode` の
FramebufferTexture）の作り直しを見ていない。描画先の大きさを「前回描いたときの値」と比べるだけなので、A → B → A の間に描かれなかった物は
更新されない。`Textures.updateTexture` が FramebufferTexture を作り直すときに参照しているバインドグループを無効にしないことも一因。
直し方の候補: 透過の材質は `FULL` にする／描画先の大きさの代わりに作り直しの回数（版）を比べる／作り直しで参照しているバインドグループを無効にする。

## AGENTS.md への提案（親が反映する）

技術の決まりごとに足す:

> - **透過の材質には必ずノードを1つ持たせる（three r186、S-12）。** ノードのない透過の材質（`MeshPhysicalNodeMaterial({ transmission })` だけ）の物は、
>   描画の大きさが A → B → A と変わる間に画面外にいると、戻ったときに破棄済みの背景画像のまま描かれる（WebGPU は毎フレーム
>   「Destroyed texture used in a submit」で描画が捨てられ、WebGL2 は「attempt to use a deleted object」）。動的解像度がプレイ中に倍率を変えるので、
>   どのシーンでも起きうる。ガラスは `createGlass()` で作るか、手で作った透過の材質を、transmission を決めた後、最初に描く前に
>   `followBackdropResize()`（`src/core/glass/backdrop.ts`）に通す。three を上げたら、S-12 の記録の最小の再現で回避策がまだ要るかを確かめる。

あわせて、センサーの提案（範囲外なので変えていない）:

- `tests/e2e/scenes.spec.ts` は各シーンを約5秒しか見ず、倍率も変えないので、この種の不具合を見逃す。案: `?debug=1` の `__vidroDebug` に
  今のシーン（`THREE.Scene`）を出し（main.ts）、scenes.spec.ts で全シーンの材質を `missesBackdropResize()` で調べて、危ない材質がないことを

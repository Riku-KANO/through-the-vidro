# S-20 速い画面でも three のタイムスタンプの読み出しが溢れないようにする

状態: **作業中** · ブランチ `slice/S-20-timestamp-drain`（main 6088cb3 から） · 担当: サブエージェント
試行: 実装 1/3（WebGL2 では、読み出しを始めた時点から終わるまで、パスごとのタイムスタンプを止める。プールの4分の1で早めに読む）

## 原因（調べたこと）

`?debug=1` から three の内部（`renderer.backend.timestampQueryPool.render`）を毎フレーム読み、読み出しの時間を測った（一時の台本。
アプリの `resolveTimestampsAsync` を包んで、呼んでから終わるまでの時間とフレーム数を取る）。

- **1フレームの描画の数**（`renderer.info.render.calls` の増え方 = `beginRender` の回数 = プールの割り当ての回数。3つとも一致した）:
  試作部屋（覗いている、仕上げあり）20、仕上げなし 3、負荷シーン 20、walk-lab 3、layers-lab（覗いている）20。
  three r186 の WebGL2 のプールは 2048 個のクエリで、描画1回に2個使うので 1024 回分。20 回なら約51フレームで埋まる（S-17 の見立てどおり）。
- **プールが空になるのは読み出しが終わったときだけ**（`WebGLTimestampQueryPool.resolveQueriesAsync` の最後で全部を消す）。main.ts は8フレームごとに、
  読み出し中でなければ読む。だから、プールに溜まるのは「読み出しが終わってから、次の読み出しが終わるまで」のフレームの全部。
- **読み出しにかかる時間**（main の実装）:

  | 条件 | 読み出しの時間（中央値 / 最大） | フレーム数（中央値 / 最大） | プールの最大 |
  |---|---|---|---|
  | 垂直同期あり 60fps（負荷シーン） | 22 / 28 ms | 1 / 1 | 360 |
  | `FPS=144`（フレームの上限、下の計測の節） | 5.5 / 8.3 ms | 0 / 1 | 360 |
  | `FPS=240` | 3.5〜4.7 / 6.2 ms | 1 / 1 | 360 |
  | `FPS=480` | 3〜7 / 18 ms | 1〜3 / 8 | 640 |
  | 垂直同期なし 533fps（負荷シーン） | 130 / 146 ms | 67 / 72 | 2040 |
  | 垂直同期なし 599fps（試作部屋） | 29 ms（8秒で2回しか終わらない） | — | 2048 |
  | 垂直同期なし 822fps（試作部屋、ホーム。描画 2回/フレーム） | 85 / 1745 ms | 111 / 1177 | 2048 |

- **考えられる理由**（未確認）: three は読み出しで、クエリごとに `setTimeout(…, 1)` で結果が出たかを見に行く。垂直同期なしではアニメーションの
  フレームが休みなく続くので、このタイマーが後回しにされ、読み出しが数十〜千フレームかかる。フレームの上限を固定すると（480fps でも）
  フレームの間に手が空くので、数 ms で終わる。
- **溢れると読み出しも止まる**: プールが満杯になると three は入れ子の描画の途中でも全部を消し（警告の原因、S-11）、同じクエリを新しい描画に
  使い回す。読み出し中のクエリが使い回されると、その結果がなかなか出ない。試作部屋で、8秒の間に読み出しが2回しか終わらなかったのはこのため
  と考えられる（ベンチのパスの合計も `n/a` になっていた）。

## 直し方（受け入れ条件2）

`src/dev/timestamp-drain.ts`（新規）の `PassTimestampDrain` が、パスごとのタイムスタンプを書くフレームと、読み出す時を決める。main.ts はそれに従うだけ。

- **WebGL2 では、読み出しを始めた時点から終わるまで、パスごとのタイムスタンプを止める**（`backend.trackTimestamp = false`）。読み出し中は
  クエリを使わないので、プールに溜まるのは「読み出しが終わってから次に読むまで」のフレームの分だけになる。8フレームごとに読むので、
  1フレーム 20 回の描画なら最大 160 回分（320 個）。**読み出しの時間にもフレームの速さにもよらない。**
- **プールの4分の1（描画 256 回分）が埋まったら、8フレームを待たずに読む**（WebGL2）。1フレームの描画が 128 回を超える場面でも、
  1フレーム約 770 回まで溢れない。数えるのは `renderer.info.render.calls`（three の公開の値。描画を始めた回数の累計で、プールの割り当てと一致する
  ことを上で確かめた）。フレームの外の描画（シーンの `update()` やプロミスの中の描画）も、タイムスタンプが有効な間なら数える。
- 読み出しを始めた直後に `trackTimestamp` を切る。three は `resolveTimestampsAsync` を呼んだ時点で `trackTimestamp` を見る（切れていると
  「Timestamp tracking is disabled」を警告する）ので、呼んだ後に切る。タイムスタンプを書かなかったフレームの後には読まない。
- **値の意味は変わらない**: three の読み出しの値は「最後のフレームのパスの合計」で、読み出しを始める直前のフレームの値であることは前と同じ。
- **WebGPU は前のまま**（止めない・早めに読まない）。WebGPU のプールは読み出しを始めた時点で自分を空にし、入れ子で衝突する「進行中の
  クエリ」もない。さらに、タイムスタンプが有効な間に作られたパスの記述子は `timestampWrites` を持ち続ける（main.ts の既存の注意）ので、
  切ったり入れたりしない。単体テストで、WebGPU の判断（8フレームごと・重ねない・止めない）が前と同じであることを確かめる。
  governor が使う span（`GpuSpanTimer`）には触れていない。

### 値と動きを変えないことの確かめ（受け入れ条件2）

main と S-20 のビルドを交互に、同じ URL で測った（`bench=5`、中品質、ヘッドレス。前後ともほかの Playwright のブラウザなし）。

| 経路・条件 | 値 | main | S-20 |
|---|---|---|---|
| WebGPU、垂直同期なし（2回ずつ） | 負荷シーンの span 平均 | 0.99 / 1.09 ms | 1.02 / 1.04 ms |
| 同 | 試作部屋の span 平均 | 0.87 / 0.92 ms | 0.87 / 0.86 ms |
| WebGL2、`FPS=60`（3回ずつ） | 負荷シーンのパスの合計 平均 | 5.72 / 4.28 / 7.92 ms | 8.67 / 5.64 / 4.79 ms |
| 同 | 試作部屋のパスの合計 平均 | 6.48 / 4.72 / 8.62 ms | 9.20 / 5.81 / 5.43 ms |

- WebGPU の span は揺れの中で同じ。WebGPU の判断はコードの上でも前と同じ（単体テストで、8フレームごと・重ねない・止めない）。
- WebGL2 のパスの合計（Apple では信用しない値。パスが重なり、60fps では GPU の時計も下がる）は、同じビルドの中でも 4〜9 ms と揺れ、
  main と S-20 の幅は重なる。止めることで値が偏る様子はない。読む値は前と同じく「読み出しを始める直前のフレームの合計」。
- 60fps のセンサーと動的解像度の e2e は `scripts/check.sh --full` で緑（下の「検査の結果」）。

## 計測と計算（受け入れ条件3）

### フレームの上限を固定する手段（`scripts/bench-probe.mjs`）

`FPS=<n> node scripts/bench-probe.mjs '<URL>' …` で、ページのスクリプトより先に `requestAnimationFrame` を包み、1000 / n ms ごとの
時計に合わせてフレームを出す（その時刻までタイマーで待つので、フレームの間はスレッドが空く。その画面の垂直同期に近い）。
垂直同期は外して起動する（`UNCAPPED_ARGS`）。遅れたフレームを後でまとめて出すことはしない。結果のフレーム時間は 60.0 / 144.0 / 240.0 /
360.0 / 480.0 fps ちょうどになった。

### 計測（Apple M5 Pro、ヘッドレス、1280×720、中品質、WebGL2。前後ともほかの Playwright のブラウザなし）

`bench-probe` の警告の数（`bench=5`。試作部屋は行き止まりで覗いている、負荷シーン）:

| フレーム | main（6088cb3）| S-20 |
|---|---|---|
| `FPS=60` | 0 / 0 | 0 / 0 |
| `FPS=144` | 0 / 0 | 0 / 0 |
| `FPS=240` | 0 / 0 | 0 / 0 |
| `FPS=360`、`FPS=480` | 0 / 0 | （測っていない） |
| 垂直同期なし（530〜610fps） | 41〜49 / 49 | 0 / 0 |

プールの最大と読み出しの時間（一時の台本で毎フレーム見た。6秒。描画は 20 回/フレーム。プールは 2048 個）:

| フレーム | main: プールの最大 / 読み出し（中央値・最大） | S-20: プールの最大 / 読み出し（中央値・最大） / 6秒で終わった読み出し |
|---|---|---|
| `FPS=144` | 360 / 5.5・8.3 ms | 320 / 5.2〜5.4・7.5 ms / 107〜108 回 |
| `FPS=240` | 360 / 3.5〜4.7・6.2 ms | 320 / 3.6〜4.6・12.5 ms / 178〜180 回 |
| 垂直同期なし | 2040〜2048 / 試作部屋は8秒で2回しか終わらない | 320 / 126〜208・220 ms / 30（試作部屋）・49（負荷シーン）回 |

- **144・240fps 相当では、main でも溢れていなかった**（S-17 の見立てどおり）。読み出しが数 ms で終わり、プールは最大 360 個（描画 180 回分）。
- S-20 では、どのフレームの速さでもプールの最大は 320 個（8フレーム × 20 回 × 2）。読み出し中に何も溜まらないので、読み出しが 220 ms
  かかる垂直同期なしでも同じ。
- 垂直同期なしの試作部屋で、パスの合計が再び取れるようになった（main ではベンチの `pass sum` が `n/a`、S-20 では 3.6〜3.9 ms）。

### 計算（`src/dev/timestamp-drain.test.ts` の「three keeps up at any frame rate」）

main.ts の読み出しの判断（`PassTimestampDrain`）を、three r186 の WebGL2 のプールのモデル（1024 回分、読み出しが終わると空になる、
満杯で自分を消す＝警告）に、1フレーム 20 回の描画と、上で測った読み出しの時間（各フレームの速さで一番長かった値をフレーム数に直す）で
4000 フレーム回す。

- S-20 の方針: 60（垂直同期 28 ms）・144（14.1 ms）・240（12.5 ms）・480（17.7 ms）・554（220 ms）・600fps（1745 ms）のすべてで溢れは 0、
  プールの最大は 8 × 20 = 160 回分以下。1フレームの描画 1〜769 回 × 読み出し 0〜2000 フレームの組でも溢れは 0。
- main の方針（止めない）: 144・240fps は溢れ 0。垂直同期なし（554fps・220 ms）は溢れる。main の方針では、プールに溜まるのは
  「読み出しが終わってから次が終わるまで」の 8 × ⌈(L + 1) / 8⌉ フレーム（L は読み出しのフレーム数）。20 回/フレームで 1024 回を超えるのは
  L ≥ 48 のとき。**144fps なら 333 ms、240fps なら 200 ms 以上かかる読み出しで溢れていた**。S-20 ではこの条件がなくなる。

- **e2e**（main の実装、2回とも同じ落ち方。`pnpm exec playwright test tests/e2e/S-20-timestamp-drain.spec.ts`）:
  - 試作部屋: 警告 58件 / 57件で落ちた。プールの最大 2048 / 2048、読み出しが終わった回数 3 / 2（6秒）、587〜609fps、1フレームの描画 20。
  - 負荷シーン: 警告 47件 / 46件で落ちた。プールの最大 2040 / 2040、読み出し 47 / 47 回、538〜543fps、1フレームの描画 20。
- **単体テスト**（`PassTimestampDrain` を main の方針に戻した版。`pauseWhileReading` を無視して常に止めない）: 16件中7件が落ちた。
  「読み出し中は書かない」（20フレームすべて書いた）、「4分の1で早めに読む」（`[]`）、「フレームの外の描画も数える」（`[7]`）、
  モデルの 480fps（最大 320 > 160）、540fps と 600fps（溢れ 50回・76回）、「読み出しの時間によらず溢れない」（1回/フレーム・読み出し2000フレームで溢れ1回）。
- **単体テスト**（2つ目の改善の前）: 「読み出しを始めた直後のフレームの外の描画もクエリを使わない」が `expected 304 to be less than or equal to 32`

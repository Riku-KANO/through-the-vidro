## 結論

- **three r186 の不具合。** 透過の背景画像は描画先ごとに写される（`ViewportTextureNode` が描画先ごとに `FramebufferTexture` を
  既定の1枚から `clone()` する）。r186 の `Texture.copy` は `source` を共有するので、**全部の描画先の背景画像が1つの
  `{ width, height }` の記録を共有する**。three はコピーの前にその記録と描画先の大きさを比べ、違うときだけ背景画像を作り直す。
  2つの描画先が別の時に透過を描き、その間に描画の大きさが変わると、先に描いた方が記録を新しい大きさにして作り直され、
  後から描いた方は「記録はもう自分の大きさ」なので作り直されず、**古い大きさの背景画像のまま残る**。
- 序章をホームから始めると、透過を描く描画先が2つある: ホームの玉の中の像（`dive-host.ts` の `innerRT`）と、着地の後の部屋の
  仕上げの scene pass（`peek-pipeline.ts` の `pass()`、テクスチャ名 `output`）。scene pass は読み込みの途中に1回だけ描かれ
  （`world.warm()`）、その後は着地まで描かれない。
- 黒い画面になる形: **scene pass が最初に描かれた時（読み込み中）の倍率が 0.8 で、着地の時が 0.85**。ホームの間に玉の中の像が
  記録を 1088×612 にするので、着地の後の scene pass は 1024×576 の背景画像へ毎フレーム 1088×612 を写そうとする。WebGPU は
  `Texture copy range … touches outside of [Texture (unlabeled 1024x576 px, TextureFormat::RGBA16Float)]` で、その submit
  （`renderContext_8`）がまるごと捨てられ、毎フレーム黒（黒の割合 96%）。S-27 の追跡に残った console と同じ文面・同じ大きさ。
- 倍率が動くのは動的解像度。読み込みの最初の重いフレームで GPU 時間が上がると 1 段（0.85 → 0.8）下げ、約 3 秒後に戻す。
  機械が混んでいると下がるのが早く、scene pass の最初の描画より前に下がる。WebGL2（Apple）は GPU 時間を信用しないので
  動的解像度が動かず、自然には起きない（大きさを強制すると WebGL2 でも起きる。下の「再現」）。
- **直し方**: 共通部品に `ownBackdropImage(target)` を足し、透過を描く2つの描画先（玉の中の像、scene pass）の背景画像に、
  最初に描く前に自分の記録（新しい `THREE.TextureSource`）を持たせた。公開の API だけ（`ViewportTextureNode.getTextureForReference`、
  `Texture.source`）。three r187 の直し（mrdoob/three.js#34636: `FramebufferTexture.copy()` が image を写した新しい source を持つ）と
  同じ形で、r187 以上では何もしない。

## 再現の条件

- **どの描画先が**: 着地の後に描く方。序章では部屋の仕上げの scene pass（`pass()` の描画先、RGBA16Float）の透過の背景画像。
  ホーム経由の sandbox の町（`home-dive`）では、着地の後の画面（three が内側で使う画面用の描画先）の背景画像と、戻った後（Esc）の
  玉の中の像の背景画像。
- **どの大きさの変化で**: その描画先が最後に背景画像を作ったときの大きさから、次に描くまでの間に描画の大きさが変わり、その間に
  もう1つの描画先が新しい大きさで透過を描いたとき。
  - 新しい大きさの方が大きい（0.8 → 0.85 など）: コピーが範囲の外。WebGPU は validation error で submit が捨てられ黒。WebGL2 は
    `GL_INVALID_VALUE: glCopyTexSubImage2D: Offset overflows texture dimensions` の warning（画面は黒くならないが、ガラスの奥が古い）。
  - 小さい（0.85 → 0.8）: メッセージなし。ガラスの奥の景色が約 6% ずれ、端に古い絵が残る（センサーは「古い大きさへのコピー」で数える）。
- **いつ**: 着地した最初のフレームから、倍率がまた変わるまで毎フレーム。自然には、読み込み中の scene pass の最初の描画（ローディングの
  「compile game (screen)」）より前に動的解像度が 1 段下がり、ホームか潜る途中で戻ったとき。
- **S-27 の「0.1 秒ごとの見本ではずっと 0.85」とは食い違う（説明できていない）。** この再現（混雑あり）で S-24 と同じ見本の取り方
  （待つ間 100ms ごとに `page.evaluate` で `__vidro.renderScale`）を足して 8 回流すと、黒になった 3 回を含めて全部で 0.8 が 15〜20 回
  見えた（見本の間隔の最大 0.98〜1.47 秒）。一方 S-27 の黒では、scene pass の背景画像が 1024×576 で作られている（three はその描画先の
  大きさで作るので、その時の描画の大きさは 0.8 倍だった）のに、見本に 0.8 が無い。考えられるのは、(a) 0.8 の間ページの主スレッドが
  止まって見本が取れなかった（S-27 の黒は機械が混んでいた時間帯に起きた。governor は1フレームの dt を 0.1 秒で切るので、
  0.8 が見えないほど短いとは考えにくい）、(b) 動的解像度以外の何かが描画の大きさを変えた、(c) S-24 の見本は `page.goto`（load の
  イベント）が終わってから取り始めるので、混んでいて goto が遅れ、最初の見本が 0.8 の時間の後だった（ここの機械では最初の見本は
  goto の約 0.08 秒後で、0.8 に下がるのは約 1.5 秒後。レビュー1巡目の仮説）。S-27 の `landing-webgpu.json` は後の実行で上書きされて
  残っていないので、どれも確かめられない。どれでも結果の仕組み（scene pass の背景画像が古い大きさで残る）は同じで、直し方は何が
  大きさを変えたかによらない。次に起きたときのために、S-29 の追跡はページの中で倍率の変化を時刻つきで残す（提案 3）。

### 追跡（`?debug=1` の範囲）

e2e の `installTracer`（`page.addInitScript`）が、main.ts が `window.__vidroDebug` を出した瞬間（最初のシーンの前）に、その renderer の
インスタンスの3つの関数を包む。main.ts は変えていない（理由: `?debug=1` の renderer で足りる。three 自身も `setPixelRatio` を同じ値で
呼ぶので、値が変わったときだけ残す）。

- `setPixelRatio`（`setScale` の行き先。倍率 × 端末の画素比）、`setSize`: 値が変わった時刻と値
- `copyFramebufferToTexture`（透過の背景画像のコピー）: 背景画像ごとに、作り直された時刻・描画先・大きさ。作り直されていない
  （テクスチャの `version` が前のコピーと同じ）のに `image` の大きさが作った時と違えば「古い大きさへのコピー」として数える。
  three の公開の値（`version`・`image`・`getRenderTarget()`）だけを使う。
- テストが `setScale` を呼んだ時刻と、読み込み・ホーム・着地・戻った時刻の印
- 書き出し: `artifacts/S-29/<case>-<backend>.json`（確かめる前に書く。途中で止まっても書く）

## 原因

three r186 の2つの仕組みの組み合わせ（`node_modules/three/src/nodes/display/ViewportTextureNode.js`、`textures/Texture.js`、
`renderers/common/Textures.js`）。

1. `ViewportTextureNode.getTextureForReference(reference)` は描画先ごとに `defaultFramebuffer.clone()` を持つ。`clone()` は
   `new FramebufferTexture().copy(this)` で、`Texture.copy` は `this.source = source.source`。**全部の写しが1つの source
   （image = `{ width, height }`）を共有する**。透過の前面の背景画像は three の中の1つのノード（`viewportOpaqueMipTexture` の元）なので、
   全部の透過の材質・全部の描画先がこの1組を使う。
2. `updateBefore` は描画先の大きさと `framebufferTexture.image` を比べ、違えば image を書き換えて `needsUpdate`（その写しの
   version を上げる）。`Textures.updateTexture` は version が変わった写しだけを image の大きさで作り直す。コピーの大きさは image。

そのため描画先 X が大きさ A で最後に作られた後、別の描画先 Y が新しい大きさ B で先に描くと、共有の image は B になり、X が B で
描くときには比べても同じなので作り直されない。X の GPU のテクスチャは A のまま、コピーは B。

- WebGPU で黒になる理由: `copyTextureToTexture` の範囲の外は validation error で、そのコマンドバッファ（描画全体）が無効になる。
- three r187 の直し: `FramebufferTexture.copy()` が `new TextureSource(Object.assign({}, source.image))` を持つ（#34636、
  jsDelivr の dev の `src/textures/FramebufferTexture.js` で確かめた）。`tools/three-repro/README.md` の S-05 の節と同じ根。
- AGENTS.md の S-05 の決まり（画面と違う大きさの描画先に透過を描かない）とは別の症状（S-05 は違う大きさが交互に描くと毎フレームの
  作り直し、S-29 は同じ大きさへ変わったときに作り直されない）だが、根は同じ（共有の source）。

## 直し方

- `src/core/glass/backdrop.ts`（core、CHANGELOG に記録、版は案 0.10.0）
  - `ownBackdropImage(target)`: `viewportOpaqueMipTexture()`（公開の TSL）の `getTextureForReference(target)`（公開のメソッド）で
    その描画先の背景画像を取り、既定の写しと source を共有していれば、image を写した新しい `THREE.TextureSource` を持たせ、
    `needsUpdate` を立てる（レビュー P3-2: 最初の描画の後に呼んでも、次の描画で作り直される。まだ作られていなければ手間は増えない）。
    r187 以上（共有していない）では何もしない。2回呼んでも同じ。
  - `sharesBackdropImage(target)`: まだ共有しているか（単体テストと確かめのため）。
  - **届くのは前面の背景画像だけ**（レビュー P2-1）。three は `side: BackSide` の透過と、`forceSinglePass` のない `DoubleSide` の透過
    （先に裏面だけを別のパスで描く: RenderList の `needsDoublePass`、Renderer の `_renderTransparents`）を、PhysicalLightingModel の
    中の別のノード（`viewportBackSideTexture`）で描く。そこには公開の口がなく、r186 では共有のまま残る。そういうガラスには
    `forceSinglePass = true`（前面だけで描く。序章のパネルのガラスがそう）。今のゲームには該当がない（パネルは forceSinglePass、
    ドームは安価な表現、glb に doubleSided のガラスはない。レビューで確かめた）。ただし `src/game/assets/glass.ts` は glb の
    DoubleSide を `forceSinglePass` なしで写すので、Blender で doubleSided のガラスを足すと裏面だけ S-29 が戻る（提案 4）。
- `src/ui/home/dive-host.ts`: 玉の中の像（`innerRT`）を作った直後に `ownBackdropImage(innerRT)`。どの世界（序章の scene pass、
  町の画面）と組んでも、玉の中の像が共有から外れるので、残る描画先が1つになる。
- `src/game/orb/peek-pipeline.ts`: scene pass を作った直後に `ownBackdropImage(this.scenePass.renderTarget)`。ホームなしでも、
  仕上げの scene pass が共有から外れる（stress も同じ組み立てだが、透過を描く描画先が1つなので変えていない）。
- 選んだ理由
  - 原因の場所（描画先ごとの背景画像が記録を共有すること）を、本家の直しと同じ形で直す。毎フレームの手間はない（作るときに1回）。
  - three の非公開の内部に触らない。頼っているのは「`getTextureForReference` が返す写しが、three がその描画先のコピーに使うもの」で、
    単体テストが three 自身の `updateBefore` で確かめる。「透過の材質がこのノード（`viewportOpaqueMipTexture` の元のシングルトン）を
    読む」ことは単体テストでは確かめられない（three の PhysicalLightingModel の中のモジュール変数）。three がここを変えると単体テストは
    緑のまま回避策が空振りし、気づけるのは S-29 の e2e（`check.sh --full`）だけ（レビュー P3-3。テストのコメントにも書いた）。
- 退けた案
  - 既定の写し（`getTextureForReference(null)`）の `clone` をインスタンスの上で包み、three が作る写しを全部分ける（呼び忘れがない）:
    three の物のメソッドを差し替えることになり、「公開の API だけ」から外れる。描画先ごとに呼ぶ形にして、呼び忘れは提案 1 の決まりと
    提案 2 のセンサーで防ぐ（レビュー P3-4）。
  - 倍率を変えたら全部の描画先の背景画像に `needsUpdate` を立てる（main.ts から）: 描画先を知っているのは各部品で、main.ts からは
    届かない。立てる時を間違えると同じ不具合が残る。
  - 着地の直前に scene pass を1回描き直す: 共有の記録がもう新しい大きさなので、描き直しても作り直されない。
  - 玉の中の像の大きさを画面と1画素ずらして、毎回作り直させる: S-05 の決まり（画面と違う大きさの描画先に透過を描かない）に反する。
  - 動的解像度を読み込み中・潜る間は止める: 起きる形を減らすだけで、Esc で戻るとき・遊ぶ途中の倍率の変化には効かない。
  - three を r187 に上げる: 依存の変更は発案者の判断（判断待ち 2）。

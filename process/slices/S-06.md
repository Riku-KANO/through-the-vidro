# S-06 M0統合 — 序章の試作部屋（歩く→覗く→置く→渡る→雫）

状態: green（2026-10-21。結果は下の「結果」）· 担当: S-06 エージェント

## 目的

S-01〜S-05（と、間に合えば S-09 の音）を1つの部屋で組み合わせ、M0 ゲートの「覗く操作が気持ちいい」を発案者が判断できる試作にする。
設計書の該当節: パズル設計 > 難易度の曲線（序章: 失敗のしようがない一本道で「覗く→置く→渡る」を体で覚える）、パズル設計 > 原則、空間の可読性と導線、進行構造とエリア設計（序章「工房」）。

## 各スライスから使うもの（2026-10-21 時点の各記録より）

| 元 | 使う口 | 統合での扱い |
|---|---|---|
| S-03 | `PlayerController`（Rapier のキャラクター制御）、`InputSystem` のイベント（peekStart / peekEnd / interact / pause）、移動速度の倍率と視野角の加算 | 歩く・視点・入力はこれに一本化する |
| S-02 | `LayerField.assign(obj, 'surface' \| 'back' \| 'shared')`、手の玉の覗く合成、実体化（0→4m、0.8秒）、`canPeek` / `canPlace` / `canPickUp`、`activeSegmentIds`、`peekMoveSpeedMultiplier()` | 層と玉の状態はこれを使う。lab の簡易な歩行と当たり判定は使わない |

## つなぎ目（統合で新しく書くもの）

1. **裏の足場と Rapier**: S-02 の足場の区画ごとに Rapier の当たり判定を作り、`activeSegmentIds` に入った区画だけ有効にする。実体化の境目には見えない柵を置く（設計書: 外へは踏み出せない）。拾う前の「足場の上にいないか」は S-03 のプレイヤーの位置から判定する。
2. **入力 → 玉**: peekStart / peekEnd → 覗く（置いている間は `canPeek` で拒否し、玉が震える）。interact → 台座の近くなら置く、置いてあれば拾う（`canPickUp` が false なら震える）。
3. **玉 → プレイヤー**: 覗く進み具合（peekAmount）で速度の倍率 0.5 と視野角 -6度を混ぜる（S-03 の weight 付きの修飾子）。
4. **部屋**: 序章の一本道。工房の作業台で玉を手にする → 行き止まり（崩れた床の先は谷）→ 覗くと裏の橋が見える → 台座に置くと橋が実体化 → 渡る → 光の雫に触れる。空間の可読性の9ルールのうち、歩ける面は透明にしない（1）、行き止まりには理由を置く（9）、次の場所が先に見える構図（6）を必ず満たす。
5. **入口**: ホーム → 潜る遷移の着地点を、この部屋の作業台の前（目の高さ1.6m、視野角70度）にする。

## 受け入れ条件（spine の S-06 を具体化）

- ホームから潜って工房に立ち、行き止まりの先を覗くと裏の橋が見え、台座に玉を置くと橋が実体化して渡れ、光の雫に触れられる
- e2e が入力を送って、潜る → 歩く → 覗く → 置く → 渡る → 雫、を最初から最後まで通しで確かめる（両経路）
- 置いている間は覗けない、橋の上では拾えない、が実際の操作で確かめられる
- 両経路で予算内、エラーなし。中品質で負荷シーン以下の重さ（`QUIET=1` の実機ベンチで比べる）
- スクリーンショット（覗く途中・実体化の途中・渡った後）を見て、設計の柱（特に「迷わずに彷徨える」「一枚絵になる」）に照らして判断できる

## 気をつけること（各スライスの知見）

- 透過の材質を、画面と違う大きさの描画先に描かない（AGENTS.md）。S-02 の `assign` を通せば自動で守られる。
- 影のカメラの layers は S-02 の `assign` が固定する。影を使う光源を足すときも `assign` を通す。
- S-02 の `renderGroup` の共有 uniform は1フレーム内の2回目の描画で更新されない（S-02 の記録）。覗くパスの切り替えは物ごとの uniform で。
- 性能の比較は並列の作業が止まっているときに `QUIET=1` で。

## 判断待ち（発案者へ）

1. **最初の操作は「作業台の玉を手に取る」**: 着地したとき玉は作業台の上にあり、E（左クリック）で手に取る（世界観 > 主人公「作業台に一つだけ残っていたビードロを手にする」、S-06 の計画「工房の作業台で玉を手にする」）。
   潜った直後に手の玉が画面に急に出ないので、潜る遷移の継ぎ目も見えない。これでよいか。
2. **見えない柵の範囲**（S-02 判断待ち4）: 「裏の足場の上にいるときだけ、球の外へ出られない」にした。共通の地面（向こう岸）では効かず、球の中に閉じ込められることはない。
3. **雫の行き先**: 雫に触れると台座の上の玉へ飛んで入る（そのとき玉は手にない）。設計の「手の玉の中に入っていく」を「玉の中」と読んだ。
4. **雫を取った後と向こう岸の門**: 試作は雫で終わる。向こう岸の奥は閉じた門（格子越しに街と灯塔）にしたが、設計で「閉ざされた扉」は表にだけある物で、ルール9の「理由」（台座か裏の層の気配）でもない。
   また玉は台座の上（向こう岸からは届かない）なので、先へ進むには戻って拾う必要があるが、拾うと橋が消えて向こう岸へ戻れない。
   本編でどうつなぐか（雫を取ると門が開く、向こう岸に2つ目の台座、橋が残る など）は設計書にない。
5. **雫は E で触れる**（基本の動作の「調べる: 光の雫に触れる」）。歩いて触れるだけで取れる形にするか。
6. **影を一度だけ描く**: 設計の「静止した影は焼き込み」の代わり。品質プリセットの「動く物の影 1024px」は、序章には影を落とす動く物がほとんどないため使っていない。
   低品質（動く物の影なし）でも焼き込みの代わりとして 1024px の地図を一度描いている。毎フレーム描くと WebGL2 で警告が増える件（分かったこと1）にも効く。
7. **操作の案内の一行**: 「ゲーム中は常時表示なし」から外れるが、M0 の体感評価で操作に迷わないため、視点を固定していない間の最初の8秒だけ出す。本編で出すか。
8. **覗いている最中の左クリック**: S-02 判断待ち3 のとおり、鳴る（エリア3）を得る前は「置く・拾う・調べる」になる。
9. **重さの比較**（spine の受け入れ条件）: 親が並列の作業が止まっているときに `QUIET=1 node scripts/bench-headed.mjs` で prologue-proto（`?bench` は覗いている視点）と stress を比べる。

## 分かったこと（失敗をルールに変える）

1. **WebGL2 の GPU タイムスタンプのプールが入れ子の描画の途中で壊れる（three r186）**: `WebGLTimestampQueryPool` は 1024 の描画（2048 クエリ）で満杯になると、
   `allocateQueriesForContext` の中で `activeQuery = null` に戻す。それがメインの描画の中に入れ子になった描画（RenderPipeline の `pass()`、影の地図）の開始で起きると、
   外側のクエリが動いたまま次の `beginQuery` が走り、`WebGL: INVALID_OPERATION: beginQuery: a query is already active for target` が出る（そのフレームの計測が欠けるだけで絵は壊れない）。
   main.ts はタイムスタンプを使うとき（`stats=1`・ベンチ・信用できる GPU）しかプールを読まないので、使わないときは満杯になる。
   - 確認: 序章で約30秒に2〜5回。`stats=1`（main.ts が8フレームごとに読む）では0回。walk-lab（影を毎フレーム）でも6秒で1回、stress（影＋多数のパス）で6秒に6回出る。layers-lab は1フレームのパスの数の偶奇の巡りで入れ子の側に当たらず0回。
   - 既存のセンサー（`scenes.spec.ts`）は console の error しか数えないので見逃していた。S-06 の e2e は warning も数える。
   - 序章の回避: `prologue-proto.scene.ts` が WebGL2 のときだけ 64 フレームごとに `renderer.resolveTimestampsAsync('render')` を描画の外で呼び、プールを空にする。
     main.ts（S-08）がタイムスタンプを読むときは、その読みの1回が「直前のフレームの値」を返すだけで実害はない。本来は main.ts の仕事（提案2）。
2. **毎フレームの影の地図は、序章では使わない**: 上の入れ子の描画を1つ減らすためと、設計の「静止した影は焼き込み」の代わりとして、静止した部屋の影は一度だけ描く（S-01 の見本と同じ）。
3. **潜る遷移の着地を見えなくするには、潜る道の終点と体の視点を同じ数値から作る**: 終点の位置と注視点を出現位置の `feet + 目の高さ` と `lookDirection(yaw, pitch)` から作り、
   単体テストで「終点＝体のカメラ」を固定した。視野角は S-04 の曲線の終点（70度）＝ S-03 の既定値。
4. **柵は「当たり判定を足す」より「地面と読まない」方が S-03 の体とよく噛み合う**: 縁のやわらかい停止・安全網・吸い付きがすべて同じ地面の測定を使うので、測定に条件を1つ足すだけで、球の縁で「縁と同じように」止まる。

## 残件

- 音（S-09）: `room.events` に玉の出来事が流れているが、音はつないでいない。S-09 を統合したら `PrologueEvent` → ぽぺん（覗く・置く・拾う・震える）と雫の音を対応させる。
- ブルームとアンチエイリアス（画面の仕上げ）: `PeekPipeline` の合成の後ろにつないでいない（S-02 の口の「RenderPipeline の合成ノードの後ろにつなぐ」）。光の雫と灯りの滲みがない。
- 2回目以降の潜る遷移の短縮版、ポーズ画面（Esc は視点の固定を外すだけ）。
- 崖・作業台・炉・街の泡は M0 のコードで作った仮の形（Blender のアセットで置き換える）。
- 雫を取った後の続き（判断待ち4）。
- 読み込み中に一度 185〜970ms のフレーム（遊ぶ画面のパイプラインのコンパイル。シェーダのキャッシュが冷えていると長い）。読み込み画面の器の光が一瞬止まる。
- 開発用の固定（`peekHold` / `growHold`）は見た目と当たり判定だけを止める。進行の状態の中の球は育ちきる（固定フレームの撮影と柵の確認のための機能）。
- 実体化の途中、近くの切り口が白く飛ぶ・球の縁の近くで膜が大きな淡い弧になる（S-02 の波面の光と膜。体感で強さを決める）。
- 負荷シーンとの重さの比較（`QUIET=1`、親が静かな状態で）。

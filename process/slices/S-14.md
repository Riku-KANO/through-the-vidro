## 結論

- `?debug=1` の `window.__vidroDebug.backdropRisks()` が、今のシーンの材質を core の `missesBackdropResize()` で調べ、
  `{ roots: 調べた根, risks: 危ない材質（1つずつ） }` を返す。判定は core の関数だけ。根を歩いて材質を集める純粋な関数は
  `src/dev/backdrop-risks.ts` にあり、単体テストで確かめる。main.ts は `?debug=1` のときだけそれを読み込み（動的 import）、根を渡すだけ。
- **`sandbox.scene` だけでは足りない。** home-dive（と、ホームから始まる prologue-proto）は `sandbox.scene` がホームの場面で、
  器のある世界は別の `THREE.Scene` として玉の中の画像（`innerRT`）や画面に描かれる。そこで `?debug=1` のときだけ、main.ts が
  `renderer.render()` と `renderer.compileAsync()` を包んで、渡された根（scene や QuadMesh）を記録し、`sandbox.scene` と合わせて調べる
  （仕上げのパス、影、`QuadMesh`、`renderAsync()`、`compile()` も、この2つを通るので拾える）。記録はシーンを作り直すたびに空にする。
- センサー `tests/e2e/backdrop-risks.spec.ts` は全シーン（`src/scenes/*.scene.ts`）を WebGPU で開き、起動（`status` が `running`）から約1秒後と
  約5秒後にこの関数を呼び、1つでもあれば落ちる。home-dive と prologue-proto では、5秒後に根を2つ以上見ていることも確かめる。
  最後に**陽性の対照**: home-dive の世界（`sandbox.scene` ではない、毎フレーム描かれる場面）に危ない材質の物を足すと報告されることを確かめる。9件で約50秒。
- センサーを先に入れて、**hello・audio-lab・home-dive の3つだけが赤**、ほかの5つは緑だった（下の「赤の証跡」）。3つのシーンの手作りの透過の材質を
  `followBackdropResize()` に通して、すべて緑になった。見た目は変わらない（audio-lab と home-dive の器の見える画面はピクセル単位で同じ）。

## センサーの限界

- **見るのは2つの時点のシーングラフだけ。** 起動から約1秒後と約5秒後にある材質しか見ない。遊んでいる途中で新しく作る材質（例: 置いた玉、
  後から足す物）は見逃す。各シーンは既定のスイッチと既定のプリセット（mid）で開くので、ほかのプリセットや
  スイッチ（`direct=1`、`autoplay=1` など）でだけ作られる材質も見逃す（今、プリセットで変わる手作りの透過の材質は stress の高品質の遠景のガラスだけで、
  S-12 で直してある。glass-gallery の高品質の遠景も透過になるが `createGlass()` 製）。
- **5秒までに描きも `compileAsync()` もしない世界は見ない。** 記録に入るのは描いた・コンパイルした根だけなので、それより後に初めて描く場面
  （ホームから潜った後に初めて組む世界など）は見逃す（今の home-dive と prologue-proto は読み込みの間に世界をコンパイルして温めるので、0.02〜0.11秒で入る）。
- **調べる時点で透過でない材質は見逃す。** `transmission` が 0 で、後から上げる材質は、その時点では危ないと判定されない（今はない）。
- **描いた後にノードを足した材質は安全と判定する（見逃す）。** three はノードを持つかをシェーダを組むときに決めるので、描いた後に
  `thicknessNode` などを足しても `material.needsUpdate = true` がなければ危ないまま。センサーは今の性質を読むので、これを安全と判定する
  （逆に、描いた後にノードを外した材質は危ないと判定する）。
- **パスの間だけ差し替える材質は見ない。** 呼んだ時点の `material` を読むので、覗くパスの間だけ `LayerField` が差し替える材質や、パスが
  一時的に入れる `overrideMaterial` は見えない（`LayerField` は透過の材質を覗くパスに入れないので、今は対象がない）。
- **`renderer.render()` と `compileAsync()` を通らずに描く根は見ない。** three の公開の描き方はこの2つを通る（`pass()` の PassNode、影、
  `QuadMesh`、`RenderPipeline` も通る。r186 の `compile` は `compileAsync` の別名の getter で、`renderAsync()` は中で `render()` を呼ぶので、
  どちらも包みを通る）。PMREM が環境マップを作るときに描いた一時的な場面も記録されて調べられる（透過の材質はないので害はない）。
- **描かなくなった根も、次にシーンを作り直すまで記録に残る。** 一時的な場面（PMREM が環境マップのために描く場面など）を捨てても記録は
  持ち続けるので、捨てた場面に危ない材質があれば偽の赤になりうる（今はない）。`?debug=1` の間はそのぶんメモリにも残る。毎フレーム新しい物を
  `render()` に渡すコードがあれば記録が増え続ける（今はない）。
- **three の不具合そのものは見ない。** 判定は core の `missesBackdropResize()`（透過で、ノードの性質が1つもない）。three の判定が変われば、
  S-12 の単体テスト（`backdrop.test.ts`）と S-12 の e2e が気づく役目。
- `?debug=1` のときだけ `renderer.render` が包まれる。描画ごとに `Set` に足すだけの軽い処理だが、`?debug=1` を使う計測（S-05 の e2e など）では
  わずかに CPU の時間が増える。

  - `window.__vidroDebug` を `declare global` に足し、型 `VidroDebug` を出した（既存の e2e の `as unknown as …` はそのまま動く）

## 結論

- `?debug=1` の `window.__vidroDebug.backdropRisks()` が、今のシーンの材質を core の `missesBackdropResize()` で調べ、危ない材質を1つずつ返す。
  判定は core の関数だけ（main.ts は材質を集めて呼ぶだけ）。
- **`sandbox.scene` だけでは足りない。** home-dive（と、ホームから始まる prologue-proto）は `sandbox.scene` がホームの場面で、
  器のある世界は別の `THREE.Scene` として玉の中の画像（`innerRT`）や画面に描かれる。そこで `?debug=1` のときだけ、main.ts が
  `renderer.render()` と `renderer.compileAsync()` を包んで、渡された根（scene や QuadMesh）を記録し、`sandbox.scene` と合わせて調べる
  （仕上げのパス、影、`QuadMesh` も `renderer.render()` を通るので拾える）。記録はシーンを作り直すたびに空にする。
- センサー `tests/e2e/backdrop-risks.spec.ts` は全シーン（`src/scenes/*.scene.ts`）を WebGPU で開き、起動（`status` が `running`）から約1秒後と
  約5秒後にこの関数を呼び、1つでもあれば落ちる。8シーンで約44秒。
- センサーを先に入れて、**hello・audio-lab・home-dive の3つだけが赤**、ほかの5つは緑だった（下の「赤の証跡」）。3つのシーンの手作りの透過の材質を
  `followBackdropResize()` に通して、8つとも緑になった。見た目は変わらない（audio-lab と home-dive の器の見える画面はピクセル単位で同じ）。

## センサーの作り

- `src/main.ts`（`?debug=1` のときだけ動く。それ以外の経路に足したのは、空の記録を空にする1行だけ）
  - `backdropRisks(roots)`: 根を順に traverse し、物の `material`（配列も）と `overrideMaterial` を `missesBackdropResize()` に渡す。同じ物を
    2回数えない（根どうしが重なることがある）。材質ごとに1件。
  - `?debug=1` の準備を、最初のシーンを作る**前**に移した。シーンが読み込み中にコンパイルする世界も記録するため。`__vidroDebug` の
    `renderer` と `setScale` は前と同じ。
  - `renderer.render` と `renderer.compileAsync` をインスタンスの上で包み、渡された根を `Set` に足す。シーンを作るたび（`createScene`）に空にする。
- `tests/e2e/backdrop-risks.spec.ts`
  - `?scene=<名前>&debug=1`（各シーンの既定のスイッチ、既定のプリセット mid）。`status` が `running` になった時刻から1秒後と5秒後に呼ぶ。
  - その時点で `status` が `running` でない、`__vidroDebug.backdropRisks` がない、`window.__vidro.errors` がある、のどれでも落ちる
    （起動に失敗したシーンは何も報告しないので、黙っていることを緑と数えない）。
  - 失敗の表示は `{ "1 s": [...], "5 s": [...] }` で、どの材質が・何個の物で・いつ見つかったかが分かる。
  - `BACKENDS=webgpu,webgl2` で WebGL2 も足せる（判定は材質だけを見るので両経路で同じ。既定は WebGPU だけ）。`SCENES=a,b` で絞れる。

## センサーの限界

- **見るのは2つの時点のシーングラフだけ。** 起動から約1秒後と約5秒後にある材質しか見ない。遊んでいる途中で新しく作る材質（例: 置いた玉、
  後から足す物）や、5秒より後に組む世界は見逃す。各シーンは既定のスイッチと既定のプリセット（mid）で開くので、ほかのプリセットや
  スイッチ（`direct=1`、`autoplay=1` など）でだけ作られる材質も見逃す（今、プリセットで変わる手作りの透過の材質は stress の高品質の遠景のガラスだけで、
  S-12 で直してある。glass-gallery の高品質の遠景も透過になるが `createGlass()` 製）。
- **描いた後にノードを足した材質は見逃す。** three はノードを持つかをシェーダを組むときに決めるので、描いた後に `thicknessNode` などを足しても
  `material.needsUpdate = true` がなければ危ないまま。センサーは今の性質を読むので、これを安全と判定する（逆に、描いた後にノードを外した
  材質は危ないと判定する）。
- **パスの間だけ差し替える材質は見ない。** 呼んだ時点の `material` を読むので、覗くパスの間だけ `LayerField` が差し替える材質や、パスが
  一時的に入れる `overrideMaterial` は見えない（`LayerField` は透過の材質を覗くパスに入れないので、今は対象がない）。
- **`renderer.render()` と `compileAsync()` を通らずに描く根は見ない。** three の公開の描き方はほぼこの2つを通る（`pass()` の PassNode、影、
  `QuadMesh`、`RenderPipeline` も通る）。`renderer.compile()`（同期）と `renderAsync()` は包んでいない（このリポジトリでは使っていない）。
  逆に、PMREM が環境マップを作るときに描いた一時的な場面も記録されて調べられる（透過の材質はないので害はない）。
- **three の不具合そのものは見ない。** 判定は core の `missesBackdropResize()`（透過で、ノードの性質が1つもない）。three の判定が変われば、
  S-12 の単体テスト（`backdrop.test.ts`）と S-12 の e2e が気づく役目。
- `?debug=1` のときだけ `renderer.render` が包まれる。毎フレーム `Set` に足すだけの軽い処理だが、`?debug=1` を使う計測（S-05 の e2e など）では
  わずかに CPU の時間が増える。毎フレーム新しい物を `render()` に渡すコードがあれば、`?debug=1` の間は記録が増え続ける（今はない）。
